## 当前架构与必须补的入口

当前 `update:download` 由管理员调用，`UpdateClient.downloadAndInstall()` 在本机下载并校验包；`launchAutomaticUpdate()` 写 `request-<id>.json`，以旧 App 可执行文件的 Node 模式启动脱离主进程的 `update-helper.cjs`，旧 App 约 250 毫秒后退出。helper 等旧 PID 退出，随后挂载、暂存、移动旧 App 到备份、替换、启动新版、等健康标记，失败时尽力恢复旧版。安装阶段没有可见且持久的取消入口；“不点击下载并更新”只是在安装前放弃，**不是安装中取消**。

最小产品入口是旧版管理员确认后、退出前启动一个**独立更新控制窗口进程**，使用同一已验证的打包二进制及单独的控制模式和临时 userData，不能打开主数据库、采集器或服务。旧主进程须等控制窗口和 helper 均已接管请求并确认就绪，才退出。控制窗口持续显示 helper 发布的真实阶段和“取消更新”按钮，直到完成、撤销或需人工恢复；关闭控制窗口不等于取消，helper 的事务与恢复不依赖窗口存活。当前代码没有此模式、握手或阶段事件，均属 DEV-025 新任务。

## 阶段、按钮与结果

| 阶段 | 是否接受取消 | helper/界面语义 |
| --- | --- | --- |
| 下载、校验及 helper 接管前 | 是，立即停止下载/校验或删除已校验但未交接的包 | 旧 App 保持运行；显示“已取消下载，尚未安装”。下载流用 `AbortController`，临时文件清理与取消回执由主进程确认。 |
| helper 已接管、旧 App 正在退出；挂载/验证/暂存，旧 App 目标尚未移动 | 是，在安全检查点确认；同步 `hdiutil`/`ditto` 执行时先显示“正在取消，等待当前步骤结束” | helper 保留原 App 与真实 userData，卸载、删除暂存/下载并重启旧 App；不能以按钮点击即称已取消。 |
| 旧 App 已移入备份或新版已放到目标，健康确认尚未**持久提交成功** | 是，但语义为“取消并恢复旧版”；一旦 helper 确认便进入不可反转的回滚流程 | 停止本次候选进程，恢复旧 App 到目标，清理暂存/挂载，启动旧版；控制窗口显示恢复进度，成功后明确“已取消并恢复旧版”。回滚关键移动期间禁用重复取消，只显示“正在恢复”。 |
| 成功已持久提交 | 否 | helper 回绝迟到取消并返回 `too_late`，界面显示“更新已完成”，不再回滚新版；需要恢复旧版时走另行定义的回退流程。 |

阶段以 helper 的**耐久事务状态**为准，不以按钮状态或控制窗口本地时钟为准。对取消请求先返回“已收到”，只有 helper 完成清理/旧版恢复并写终态后才显示“已取消”。重复点击、控制窗口重开、迟到请求和成功提交竞态均须幂等。

## 最小协议、授权与数据保护

1. 由主进程的管理员授权 `update:download` 创建一次性 `requestId` 和随机取消能力；控制进程通过受限进程间通道接收能力，不在 CLI 参数、日志、遥测或渲染器页面存原值。helper 仅接受同请求 ID 的取消消息；当前登录角色变更不让普通主窗口绕过授权。控制窗口的 IPC 只接受自身主 frame，不能暴露通用文件/进程操作。
2. 在 owner-only 的 `userData/updates` 私有目录以临时文件+原子改名记录 `requestId`、阶段序号、确认水位、取消回执和终态；校验真实路径、文件所有者/权限、请求代次和随机能力，拒绝符号链接、旧请求、他人用户目录及成功提交后的请求。能力仅限制误取消与跨进程/跨用户调用；不宣称能防同一 macOS 用户的恶意进程。helper 不根据 UI 传入的任意 PID 或路径执行文件操作。
3. helper 在旧 App 退出前、挂载后、暂存后、旧版移动前、新版放置后、启动健康探测前以及成功提交前检查取消；每次文件移动及状态写入有耐久 journal，先记意图再执行，再记完成。阻塞系统调用期间不得强行杀死 helper 造成半成品；UI 展示正在等待检查点。helper 保存旧 bundle 备份到成功持久提交之后，回滚/取消均从可验证备份恢复；原始 userData 不作为安装暂存目录。
4. **健康探测先隔离数据并演练迁移**：当前新版在写 `ready-<id>.json` 前会打开并迁移真实 `token.sqlite`。为使替换后取消可恢复旧版，新增候选探测模式：先取得一致的真实 userData 快照，在 owner-only 临时目录中复制其必要数据库、凭据及队列，禁用正式服务、上报和对真实目录的写入；在该副本上实际运行新版迁移、启动与健康检查，并验证版本、bundle、数据完整性及既有登录/用量的可读性。副本只作隔离演练，终态后清理。空的无副作用目录仅能证明二进制可启动，**不能**作为真实用户数据可迁移的完整健康证据。取消时终止本次探测进程并恢复旧版，真实 userData 保持原状；快照或演练失败时在移动旧版前中止更新。成功提交后才启动新版正式会话。即使副本演练通过，正式数据迁移仍可能因外部状态失败；须保留可独立运行的旧版恢复入口、真实 userData 备份与明确反馈，在该失败时按恢复事务处理，不能把探测通过误称绝对保证。
5. 结果按请求 ID 耐久保存 `cancelled_before_install`、`cancelled_restored`、`success`、`rollback_failed` 等终态及脱敏原因。控制窗口和下一次 App 启动都可读取；展示/确认后再清除，不再由一次性 `readInstallStatus()` 的先读者删除使用户错过结果。恢复失败时保留旧版备份与 journal，明确显示备份路径的本机恢复指引，不误报已恢复。

## 崩溃、断电与最小交付边界

helper 或控制窗口异常退出时，下一次启动先检查 journal、目标/备份/暂存的实际版本和 `requestId`，按耐久阶段幂等继续或回滚；不得只看 `last-install.json` 或目录是否为空。替换中可能暂时没有可启动的目标 App，因此**仅依赖目标 App 下次启动不能保证断电后自动恢复**。最小交付须保留可独立运行的旧版恢复入口及备份，并给出从 Finder/终端打开它的清晰指引；若产品承诺断电后无需人工动作自动恢复，还须另交付不在被替换 bundle 内的开机恢复机制并做系统级验收。当前设计不把模拟进程退出等同真实断电或系统目录安装。

实际安装位置 `/Applications`、`~/Applications`、从只读 DMG 触发更新、磁盘真正耗尽、helper 被强杀、断电、签名公证及另一台 Mac 均需各自环境证据；本机临时目录的故障注入只验证所声明的隔离路径。TC-028 的发布与 Gatekeeper 目标独立保持待验。

## TC-076 新增可执行断言

- 在真实 0.3.5/0.3.6 DMG、隔离可写安装目录与无正文 1280 Token 测试用户数据中，分别在下载中、校验后交接前、旧版退出后挂载/暂存、旧版移动后和新版探测期间触发**可见按钮**取消；逐次记录控制窗口阶段、helper 回执、最终旧版版本/受信登录/用量、userData 不变、进程/挂载/暂存/下载清理及旧备份。给副本预置需要迁移的旧库与受信状态，核副本迁移成功、真实目录在取消时不变，以及副本迁移失败时尚未替换旧版；仅空目录探测不得作为通过。不能用不点击确认、直接单测 `runAutomaticInstall` 或仅预置取消文件替代打包版 UI→helper 路径。
- 在 `ditto` 等阻塞步骤中点击后应先显示等待检查点，完成后才给取消终态；重复点击、控制窗口关闭重开、viewer 或伪造请求 ID/能力、符号链接请求路径须拒绝越权或重复执行。成功提交前后各注入一次竞态，前者只能完整回滚，后者只能 `too_late` 且新版保持正常。
- 用隔离进程强杀/重启模拟 journal 恢复：在旧版移动前、两个移动之间和探测阶段中断，核备份保留、恢复操作幂等及下一次启动的脱敏结果。真实断电、真实满盘、系统安装目录与签名异机另列人工/目标环境证据；模拟不升为其通过。
