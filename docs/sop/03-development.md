# SOP-003 开发与集成

入口：已核对 `REQ → DEV → TC`，通过 [SOP-002](02-design-plan.md) 的方案检查。具体仓库命令和不可破坏的规则见[Codex 技术指南](../agent.md)。

## 执行步骤

1. **建立工作区**：查看 `git status` 和基线；保留他人的未提交改动。文档变更遵循独立 `codex/docs/YYYYMMDD-主题` 分支；代码变更使用与现有工作流兼容的隔离分支或工作区，避免混入无关修改。
2. **按任务实现**：以工作簿 `DEV` 的交付物为范围。先实现来源解析/业务规则，再接入持久化、主进程、预加载和界面；每层保持类型与错误状态一致。数据库迁移要验证旧数据、失败恢复和备份兼容。
3. **保持不变量**：重复扫描、文件替换/截断、遥测重复批次不能增加用量；来源归属显式绑定；普通用户范围由主进程限制；缺失、权限不足和未知格式不得显示为零。Codex 缓存输入/推理输出是子集，Claude Code 四类用量相加；改变口径前先更新设计和用例。
4. **编写必要验证**：每次功能迭代按变更范围修改或新增 `TC` 对应的测试，并在 `scripts/test-cases.mjs` 注册 `npm run test:case -- TC-###` 的独立调用映射。计算和解析规则用单元测试；权限、IPC、用户流程和打包主流程用 Electron Playwright。样本人工构造且不含正文；优先覆盖会导致错误计量或越权的边界，不写只重复实现细节的测试。
5. **隔离测试数据**：造数只写入专用临时测试数据库及用户数据目录，显式传入测试路径；运行器在路径缺失、指向生产用户目录或来源目录不受控时应拒绝启动。无论成功或失败均清理测试数据，不修改实际用户库。需要跨重启验证时复用同一次测试的临时库，并在用例结束后删除。
6. **自查与集成**：检查变更文件、类型、相关测试、错误路径和日志内容；按范围运行 [SOP-004](04-test-acceptance.md) 的验证。发现新需求或验收变化，返回 SOP-001 更新追溯后再继续。

## 退出检查

- 每项 `DEV` 有可审查的代码/文档落点；实现与设计一致，无真实会话 JSONL、数据库、密钥、凭证或正文日志进入 Git。
- 对应测试已实现，所有 `TC` 可按编号独立调用；人工环境不足时命令须明确返回“待验证”，失败项不得写成通过。
- 变更可构建，相关验证结果可复现；通过后进入 [SOP-004](04-test-acceptance.md)。
