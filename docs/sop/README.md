# Token 项目 SOP 入口

版本：1.0；生效日期：2026-10-02；维护会话：建立本 SOP 体系的项目会话。

本目录规定一次迭代从需求到发布、运行反馈的执行步骤。新任务先读根目录 `AGENTS.md` 和 [Codex 技术指南](../agent.md)，再按本页选择 SOP。产品事实以[设计](../design.md)为准；`REQ-###`、`DEV-###`、`TC-###` 的编号、状态和关联以[追溯工作簿](../../outputs/20261002-token-docs/Token-需求开发测试追溯.xlsx)为准；本目录不建立第二份需求清单。

## 每次任务的统一入口

1. 读取任务描述、`git status`、相关设计和现有证据，判断是**功能变更**、**缺陷修复**、**纯文档/SOP 变更**还是**发布操作**。保留工作区已有改动。
2. 功能变更和影响用户可观察结果的缺陷修复先执行 SOP-001；已有编号仍可代表同一需求，但新增能力、独立验收范围或新用例须分配新编号。纯流程文字调整不虚构 `REQ/DEV/TC`；若改动产品行为或验收标准，先更新工作簿。
3. 按 `SOP-001 → 002 → 003 → 004 → 005` 推进；不适用的阶段写明理由。运行反馈从 SOP-006 进入，再回到对应阶段。既有 M0–M4 是首版里程碑，不作为后续迭代的固定排期。
4. 每个阶段结束时核对退出条件，记录“通过 / 待处理 / 不适用”及证据。未通过的门槛不得写成已完成；可继续不依赖它的工作，并明确阻塞的下一步。
5. 交付报告包含范围与编号、实际变更、验证命令和结果、未覆盖边界、发布状态及下一步。涉及本机数据时用聚合或人工构造样本，不贴真实会话正文、数据库或密钥。

## 大模型执行约定

- 将用户任务转成可核对的产物和退出条件；先查工作簿与设计，随后实施、运行必要验证、写回真实证据。不得仅凭“代码看起来正确”把用例标为通过。
- 对规则、版本或来源格式不确定时记录假设与影响，先做只读调查或最小验证；无法取得证据时标记“未知/未覆盖”。不把未知写成零用量。
- 对权限、来源归属、去重、Token 分类、时区和导出一致性，按相关 SOP 的异常路径验证。测试只使用人工构造的无正文样本；不把真实本机记录复制进仓库。
- 每个 `TC-###` 必须有按编号单独执行的可重复命令；统一入口为 `npm run test:case -- TC-###`，注册完整性由 `npm run test:cases:check` 核对。人工/目标设备用例也由该入口给出准备步骤，实际执行后以 `npm run test:case -- TC-### pass /绝对路径/脱敏证据文件` 记录；缺少环境或证据时保持未验证，不自动判通过。
- 测试写入仅允许一次性专用测试数据库和隔离的用户数据目录；运行器须拒绝生产用户数据路径，测试后清理。每轮功能迭代交付前更新或新增受影响用例、逐项运行并留存结果，再运行 `npm run test:gate`；任何范围内用例未通过时不得交付该功能。
- 用户已明确授权的开发、文档和发布工作按请求完成。真正缺失的业务决定、证书或外部权限应说明已完成的准备和具体阻塞点，不猜测通过。
- 阶段交接使用简短格式：`目标/范围；REQ-DEV-TC；已完成与证据；未完成及原因；下一步与进入条件`。写在任务交付说明或相应记录中，不另建平行追溯表。

## 本 SOP 体系的变更控制

本会话统一受理 SOP 的新增、更新和删除。其他项目会话可以提出带理由、受影响文件和拟改退出条件的建议；在本会话完成核对与落库前，仍按已生效版本执行。仓库本身不能识别会话身份，因此以本目录的 Git 历史和登记表作为可核查的版本记录。

1. **提出**：说明触发事件、现行步骤的问题、适用范围、预计影响的 `AGENTS.md`、`docs/agent.md`、设计、工作簿及阶段 SOP。
2. **核对**：检查是否改变产品功能、验收或发布门槛；若改变，先按 SOP-001 更新对应 `REQ/DEV/TC`，再修改流程。纯流程变更不占用功能编号。
3. **编辑**：新增用下一个 `SOP-###`；修改保留编号并更新版本/日期；删除改为“废止”，在登记表保留编号、原因、替代流程和日期，修复所有入口链接，再删除或归档正文。不得悄悄消除仍在使用的门槛。
4. **校验与落库**：每次 SOP 变更从最新 `origin/main` 建立独立 `codex/docs/YYYYMMDD-sop-主题` 分支。执行 `git diff --check`、相对链接和交叉引用检查；若动了工作簿，还要检查能打开、编号唯一、三方关联、状态证据及受影响页面显示，清理临时预览文件。提交并推送文档分支，合并并推送到 `origin/main`，最后核对远端提交。若远端保护规则或权限变化，记录未完成步骤。
5. **通知执行者**：在本会话说明改动的 SOP 编号、生效提交、迁移影响以及仍待处理的门槛。已在途任务对受影响阶段重新核对，历史证据保留原日期和版本。
