# SOP-005 构建、发布与回退

入口：[SOP-004](04-test-acceptance.md) 对拟发布范围给出可核查结论。先明确本轮是**仅合入代码**、**向已安装桌面应用交付**，还是**面向其他 Mac 外部分发**。仅合入 Git `main` 时记录“代码已集成，未交付”，不得因为源码或测试通过而声称用户已获得功能。

## 执行步骤

1. **确定版本与接收对象**：拟交付桌面功能时，记录目标用户当前已安装版本、应用连接的更新服务地址/发布数据目录、更新渠道、系统架构，以及本轮新版本号。新版本必须高于已安装版本和该渠道清单的现行版本；版本号在 `package.json`、App 元数据、安装包及更新清单中一致。未决定新版本号或接收对象时停在“已集成，未交付”。
2. **冻结提交与验证**：记录唯一候选提交、版本、包含的 `REQ/DEV/TC`、已知缺口和目标环境；在该提交单独运行全部受影响 `TC` 及完整 `npm run test:gate`。更改源码、版本、打包配置或制品后，重新冻结并重跑受影响验证；不得拿旧提交的通过结果给新包背书。需要目标架构打包应用验证时运行 `npm run test:e2e:packaged` 和适用的安装/更新用例。检查 Git 中无私有数据或无关修改。
3. **制作并核对制品**：按目标架构构建目录包和 DMG（本机未签名版通常用 `CSC_IDENTITY_AUTO_DISCOVERY=false npm run pack:dir`、`npm run pack:dmg`）。核对 App 内版本、实际架构、安装包文件名/大小、`hdiutil verify` 结果及 SHA-256；记录制品与冻结提交的对应关系。存在多架构接收对象时分别制作、验证、记录，不用另一架构的包代替。制品存在不等于已发布或已安装。
4. **发布到实际更新服务**：将已验证的对应架构制品发布到**目标已安装应用实际连接的服务和渠道**，例如 `npm run publish:update -- /绝对路径/Token.dmg <版本> <arm64|x64> /实际服务数据目录`。从该服务的真实更新接口核对清单版本、架构、大小、包 SHA-256 与冻结制品一致，并确认旧版应用使用的地址与凭据确实能取得它；只写入开发临时目录或仅看到 `latest.json` 文件，不算目标用户已可更新。若一个服务清单不能同时提供多个架构，未覆盖架构保持未交付。服务地址、密钥和用户数据不写入仓库证据。
5. **从前一已安装版验收**：先备份目标应用与用户数据并确认回退路径，再由目标位置的**已安装旧版**在其原有配置下执行“检查更新 → 发现新版本 → 下载与哈希校验 → 自动退出/替换 → 重启”。核对安装路径、新版版本、账号与既有数据、相关功能和本轮适用的性能条件；性能变更须记录同一机器/数据规模、旧新版本、操作、重复次数及测量结果。隔离 DMG 升级脚本可作先行验证，但不能替代此项实际安装路径与真实服务的验收。旧版不支持自动升级或任何环节缺证据时，该交付保持未完成，并写明可用的替代安装路径及其实际验收状态。
6. **交付与记录**：在验收记录/版本规划中写明冻结提交、版本、架构、制品 SHA-256、更新服务与清单核验、旧→新版安装证据、受影响 `TC` 和完整门禁、功能/性能结果、限制及回退位置。对外说明只宣称已在目标用户和环境完成的范围；确认远端代码、发布清单和已安装版本各自指向的候选，分别标注状态。
7. **外部分发附加门槛**：若面向其他 Mac 公开分发，还须在具备材料的环境完成签名、公证、票据验证和目标设备安装检查；记录证书身份与验证结果，密钥不得入库。未通过时可保留本机未签名版的已验证子范围，但不得称外部分发完成。

## 回退与退出检查

- 发布前保留上一可用版本的制品、用户数据备份及服务清单恢复办法；数据库格式变化时说明旧版能否读取新数据。出现错误计量、越权、数据损坏、无法启动或性能退化超出本轮验收条件时停止继续分发，恢复清单或制品并按已验证流程处理数据，记录影响范围，再由 [SOP-006](06-maintenance.md) 跟进。
- 桌面功能只有在**新版本号、冻结提交与门禁、目标架构制品及哈希、实际更新服务、前一已安装版发现/下载/自动替换/重启、功能与适用的性能验收、回退准备**均有证据时，才标“已交付”。任一门槛失败、待验证或缺证据时，明确停在“已集成，未交付”“候选制品待发布”或“服务已发布，安装未验收”，列出缺项，不把 Git 合入、DMG 打包或临时服务测试当作用户交付。
