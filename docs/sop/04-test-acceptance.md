# SOP-004 测试、回归与验收

入口：实现已可检查，或修复需要回归验证。用例编号、状态和证据写回工作簿；历史事实保留在[验收记录](../validation.md)。

## 执行步骤

1. **建立验证矩阵**：从本轮 `REQ/DEV/TC` 和影响面选择测试；每次功能迭代交付前修改或新增对应 `TC`，并核对每个用例有可重复的独立命令。不把旧用例的历史通过直接当作本轮结果。标明环境、目标版本、冻结提交、应用/工具版本、数据来源和样本性质；代码或包变化后，受影响结果须在新的冻结提交上重跑。
2. **准备隔离环境**：用人工构造样本在一次性测试用户数据目录内创建专用测试数据库；确认路径不指向真实用户库或工具会话目录。测试脚本应在开始前拒绝不安全路径，并在结束时清理；清理失败视为待处理。
3. **逐用例运行**：执行 `npm run test:cases:check`，再以 `npm run test:case -- TC-###` 单独运行每个受影响编号。人工/目标设备用例先由命令读取步骤，实际执行后用 `npm run test:case -- TC-### pass /绝对路径/脱敏证据文件` 记录；环境不足或未操作时不得通过。每个拟交付桌面功能在同一冻结提交上运行完整 `npm run test:gate`；打包后运行 `npm run test:e2e:packaged` 及相关安装/更新用例，记录所测包的版本、架构和 SHA-256。实际命令、环境、退出码、通过/失败/待验证和证据位置均须留存；当前命令索引见[技术指南](../agent.md#常用命令)。
4. **核对关键路径**：采集验证原始分类、同请求和跨来源去重、重复扫描及恢复；报表验证明细与汇总、时区/ISO 周、筛选和 CSV 列结构/数值；权限验证普通用户无法通过 IPC 扩大范围；异常验证缺失、无权限、格式未知及未覆盖状态。按关联用例选择，不能用单一演示替代边界验证。
5. **处理失败**：记录复现步骤、期望/实际、影响和对应编号；修复后重跑失败用例及受影响回归。不能修复时将对应 `TC` 保持“待验证”或明确失败记录，说明发布影响。
6. **写回证据**：在工作簿测试用例证据栏记录日期、环境、按编号运行的命令、结果及必要的文件位置；同步矩阵状态。验收结论变化时给 `docs/validation.md` 追加有日期的新记录，不覆盖 2026-10-02 的原始事实。

拟通过应用内更新交付的功能，还须在 [SOP-005](05-release.md) 验证**前一已安装版本 → 目标版本**的实际路径：旧版发现更新、下载并校验、自动替换、重启以及新功能/性能。仅用当前源码启动新版本，或只在隔离目录验证旧新包，均不能代替目标用户所连接服务和已安装应用的交付证据。

## 退出检查

- 本轮每个受影响 `TC` 都已按编号单独运行，通过结果和证据一致；测试数据库与生产用户数据隔离且测试后已清理。需求和任务状态不从测试状态自动推断。
- 阻断缺陷、未验证环境和覆盖缺口已列出；发布范围内的验收条件均通过。任何范围内用例失败、待验证或无法单独运行时不得交付该功能，应回到 [SOP-003](03-development.md) 或调整范围并回到 [SOP-001](01-requirements.md)。
- 通过后形成发布候选，进入 [SOP-005](05-release.md)；此时仅可称“代码/候选已验证”，不得称“桌面功能已交付”。
