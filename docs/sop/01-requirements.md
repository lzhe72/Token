# SOP-001 需求与范围

入口：新能力、用户可见缺陷、现有验收条件变化、候选功能排期；运行反馈由 [SOP-006](06-maintenance.md) 转入。权威编号和关系见[追溯字段定义](../traceability.md)与工作簿。

## 执行步骤

1. **接收与定类**：写出问题、目标用户、触发场景、当前行为与期望行为；区分缺陷、增强、研究和纯文档。说明是否属于本机离线用量观察范围，列出不在本次范围内的能力。
2. **核对现状**：查工作簿和[设计](../design.md)，找到已有需求、任务、用例及历史证据。涉及采集格式时记录工具版本、来源类型和可观察覆盖；涉及报表时记录时间区间、时区、筛选与数据来源。不得以旧版本样本证明新版本兼容。
3. **定义验收**：把目标写成可观察结果，覆盖正常路径、失败/空数据、权限边界及必要的恢复路径。明确“未知/未覆盖”和真实零用量的区别；记录来源优先级、去重和提供方专属 Token 口径是否改变。
4. **先更新追溯**：在工作簿“需求”页新增或修订 `REQ`，在“开发任务”“测试用例”页建立 `DEV`、`TC`，在“追溯矩阵”补关联。新增独立能力或用例用下一编号；拆分保留原编号并写替代关系。为每个 `TC` 规划可按编号执行的命令及隔离测试数据。此步先于代码和测试变更。
5. **确定范围与优先级**：记录依赖、风险、验收责任和本轮交付边界。候选项只有完成范围决定及追溯后才进入实施；未确认的覆盖率、成本或外部分发能力不能写成承诺。

## 退出检查

- 每个在本轮范围内的 `REQ` 有可执行的验收条件，至少关联一个 `DEV` 和一个 `TC`；任务、用例都能回溯需求。
- 用例写清前置条件、操作、预期结果；预计无法验证的条件标为待验证并说明所需环境或样本。
- 本轮每个受影响用例有独立可运行的入口设计；无法构造安全隔离环境的用例不得进入交付范围。
- 设计与需求矛盾已消解；尚未决定的业务口径列为明确阻塞项。通过后进入 [SOP-002](02-design-plan.md)。
